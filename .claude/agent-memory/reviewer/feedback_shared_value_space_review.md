순서·자리 값(`position`) 같은 컬럼을 **두 경로가 각자 만드는** 마이그레이션을 리뷰할 때,
"각 경로가 혼자서 맞는가"로 끝내지 말고 **두 경로가 같은 값 공간을 어떻게 나눠 쓰는지**를
숫자로 굴려 본다. 전형적인 판: 새 행은 `default (nextval(seq) * K)`, 이동은 RPC가
`max + K` / 중간값으로 만든다 → **이동이 시퀀스를 앞질러** 다음 insert가 같은 값을 받는다.
유일 제약 `unique (user_id, position)`이 있으면 증상이 "순서가 이상하다"가 아니라
**"할 일 추가가 실패한다"**로 나오고, 실패한 insert도 `nextval`을 소비하므로 재시도하면
성공해 버려 재현이 들쭉날쭉해진다.

**검산 방법**: 백필 직후 상태(예: position 1024·2048·3072·4096, seq next = 5)를 적어 두고,
"맨 아래로 끌기"·"맨 위로 끌기"·"재번호"를 한 번씩 적용해 **각 분기 뒤의 max(position)과
다음 nextval*K를 나란히** 적는다. 한 번이라도 `max >= nextval*K`가 되면 그 지점이 버그다.
설계 문서가 "동순위도, 추가 실패도 없다"처럼 단정해 둔 문장은 **그 단정이 어느 분기까지
적용되는지**를 확인한다(보통 한 분기만 보고 쓴 문장이다).

**Why:** 2026-11-10 todo-reorder 리뷰에서 `move_todo`의 "맨 아래" 분기(`v_after_pos + 1024`)가
전역 시퀀스를 앞질러, 맨 아래로 한 번 끌 때마다 **다음 할 일 추가가 한 번씩 실패**하는 판을
찾았다. 마이그레이션 주석은 "nextval은 단조 증가하므로 맨 아래가 깨지지 않는다"고 적었지만
그 근거는 재번호 분기(행 수 × 1024)만 설명하고 있었다. SQL을 돌릴 수 없는 저장소라
(로컬 Docker 없음) 이 종류는 손 검산으로만 잡힌다.

**How to apply:** `supabase/migrations/`에 컬럼 기본값(시퀀스·now()·카운터)과 그 컬럼을 고치는
RPC가 **함께** 들어오는 변경이면 적용한다. 관련:
[[feedback_sql_trigger_check_verification]](경계값 대입), [[deferred-migration-write-path]](적용을
미룬 마이그레이션의 읽기/쓰기 영향 갈라 적기).
