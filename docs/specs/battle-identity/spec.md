# battle-identity 기획

## 배경 (이 문서를 왜 쓰는가)
프로젝트 오너가 현재 구현을 보고 다음과 같이 지적했다: "지금 대결 부분이 애매해. 뭘 대결하고 사람들이 어떤 걸로 증명하고 하는 과정이 명확하지 않아. 이 과정이 우리 앱의 정체성이야."

이 지적은 새 기능 요청이 아니라, 이미 구현된 핵심 기능("대결")의 개념 자체가 사용자에게 한 문장으로 설명되지 않는다는 문제 제기였다. 이 문서는 그 애매함의 원인을 진단하고, "대결"의 정체성을 명료하게 재정의한 결과를 기록한다. 아래 모든 결정 사항은 사용자 승인을 거쳐 확정됐다.

### 애매함의 원인 진단 (작성 당시 코드 기준)
1. **대결의 "대상"이 개인 투두와 분리되어 있었다.** 대결 생성 시 입력하는 것은 유형(speed/quality)과 자유 텍스트 "제목"뿐이며, 이 제목은 개인 투두 목록과 아무 관계가 없었다. "내가 원래 하려던 일을 걸고 싸운다"는 감각이 화면 어디에도 드러나지 않았다.
2. **속도전에는 증명 절차가 전혀 없었다.** 참가자가 "완료" 버튼을 누르는 순간 그대로 서버 타임스탬프가 찍히고 먼저 누른 쪽이 승리했다 — 실제로 과제를 했는지 확인하는 절차가 없었다. 반면 품질전은 증거 제출 + 상호 승인/이의제기라는 명확한 절차가 있어, "증명하는 경쟁형 투두"라는 정체성이 대결 유형의 절반에서만 성립했다.
3. **"무엇을 겨루는가"가 정의돼 있지 않았다.** 제목 필드 하나로는 "동일 과제 공유"와 "각자 다른 과제로 성실성 경쟁"이 구분되지 않았다.

## 정체성 정의 (확정)
**"투두두두는 친구와 같은 과제 하나를 함께 걸고, 각자 완료를 증거(사진)로 제출한 뒤 상대가 그 증거를 승인해야만 완료와 승부가 최종 확정되는 경쟁형 투두 앱이다. 속도전이든 품질전이든, 자기 신고만으로는 결과가 확정되지 않는다 — 반드시 상대의 승인을 거쳐야 한다. 속도전은 '누가 먼저 증명하고 인정받았는가'로 승부를 가르고, 품질전은 '증명한 결과를 서로 인정하는가'만을 본다(승자 없음). 증명 없이는 완료도, 승부도 없다."**

## 확정된 결정
### A. 대결의 기본 개념
1. **대결의 대상: 동일 과제 공유.** "대결"은 두 사람이 동일한 과제 하나를 공유하는 것으로 정의한다. "각자 다른 과제로 성실성을 겨루는" 모델은 채택하지 않는다.
2. **제목-개인 투두 연결: 비연결.** 대결 생성 시 개인 투두 항목을 지정하는 기능은 만들지 않는다. 제목은 지금처럼 투두와 무관한 자유 텍스트 라벨로 유지한다.

### B. 증명 절차
3. **속도전에도 증명 + 상호 승인 필수.** (원문: "사진 증거는 신뢰성의 중요한 포인트다. 그리고 속도전의 경우 내가 증거(사진)를 첨부하고 완료를 눌러도 상대방이 인정을 해야 한다. 내가 대충하고 끝내고 완료를 눌렀다고 이기는 건 말이 안되기 때문이다.") 속도전도 품질전과 마찬가지로 "완료 주장(증거 첨부 + 완료 버튼) → 상대의 승인/이의제기" 절차를 거쳐야 하며, 자기 신고만으로는 승리가 확정되지 않는다.
4. **품질전 증거: 사진 필수로 격상.** 텍스트만으로는 "증명"이라 부르기에 정체성상 부족하다고 판단, 사진 제출을 필수 요건으로 확정한다. `TODO_BACKLOG.md`의 "1차 배포 이후 보류" 항목에서 이번 스코프로 승격한다.

### C. 속도전 상호 승인의 세부 판정 규칙
5. **완료(승부) 확정 시각: 증거 제출 시각 기준.** 승부는 각자 증거를 제출하며 완료를 주장한 시각(서버 타임스탬프)으로 가른다 — 기존 속도전 판정 방식을 그대로 유지한다. 상대 승인은 그 완료를 "유효한 것으로 확정"하는 절차일 뿐, 승부의 시각 기준 자체를 바꾸지 않는다.
6. **양쪽 모두 증거를 제출해야 한다(대칭 구조).** 속도전에서도 두 참가자가 각자 증거를 제출하고 서로 상대의 증거를 판정해야 대결이 종결된다. "먼저 낸 사람만 승인받으면 즉시 끝"나는 비대칭 모델은 채택하지 않는다. 이유: 먼저 낸 사람이 대충 했다면, 늦게 냈지만 제대로 해낸 사람이 이길 수 있어야 하기 때문이다.
7. **이의제기(dispute) = 그 사람의 완료 무효화.** 이의제기를 당한 참가자의 완료는 무효가 되고, 승인받은 참가자의 완료만 유효하다. 속도전 결과는 유효한 완료들 사이에서 결정된다:
   - 양쪽 다 승인받음 → 증거 제출 시각이 빠른 쪽 승리 (결정 5번)
   - 한쪽만 승인받음 → **승인받은 쪽 승리** (제출이 늦었더라도, 이의제기당한 상대의 완료는 무효이므로)
   - 양쪽 다 이의제기당함 → 유효한 완료가 없으므로 승자 없이 `disputed`
   품질전은 승자 개념이 없으므로 기존대로다 — 양쪽 다 승인되면 `finished`, 하나라도 이의제기되면 `disputed`.
8. **증거 재제출: 항상 허용하며, 제출 시각도 함께 갱신된다.** 이의제기를 당한 뒤든 아직 판정 전이든, 참가자는 증거를 다시 제출할 수 있고 이때 판정(`decision`)은 리셋되고 제출 시각(`evidence_submitted_at`)도 새로 갱신된다. 실수로 잘못된 사진을 올린 경우를 복구할 수 있게 하되, 제출 시각이 밀리므로 "일단 대충 빨리 내고 이의제기당하면 그때 제대로 낸다"는 전략이 이득이 되지 않는다. (참고: 이는 기존 `submit_quality_evidence`의 동작과 동일하므로 별도 가드가 필요 없다.)
9. **속도전/품질전 차별점: 승자 유무 차이로 충분.** 두 유형 모두 "증거 제출 → 상대 승인/이의제기" 구조를 공유하지만, 목적 자체가 다르다(속도전=승부 확정, 품질전=상호 인정)는 것으로 구분에 충분하다. 승인 제한시간 같은 추가 차별화 장치는 만들지 않는다.

## 사용자 스토리
- 친구와 경쟁하며 할 일을 끝내고 싶은 사용자로서, 대결을 만들 때 "우리가 지금 무엇을 걸고 겨루는지"가 명확한 개념으로 표현되기를 원한다.
- 대결에 참가한 사용자로서, 상대가 "완료"를 주장했을 때 그것이 증거로 뒷받침되고 내가 직접 승인해야만 확정된다는 것을 신뢰하고 싶다. "대충하고 완료 버튼만 누르면 이기는" 구조는 이 앱의 정체성(증명)을 스스로 무너뜨리기 때문이다.
- 대결 결과를 나중에 돌아보는 사용자로서, 전적 화면에서 "무엇을 걸었고 어떻게 증명되었는지"를 유형에 상관없이 일관되게 이해하고 싶다.

## 범위 안
- 위 9가지 확정된 결정 전부.
- 속도전 진행 화면에 증거(사진) 제출 + 완료 주장 UI, 상대 증거에 대한 승인/이의제기 UI 신설.
- 품질전 증거 제출을 사진 필수로 변경(현재 텍스트만 지원하는 것에서 변경).
- 속도전이 disputed 상태로 전이될 수 있도록 상태 전이 규칙 확장(현재는 품질전만 disputed 도달 가능).

## 범위 밖
- AI 심판, 증거(사진) 업로드의 기술적 구현(Storage 버킷/RLS 등 인프라), 대결 생성/진행 화면의 구체적 UI — 이 문서는 개념과 규칙 정의만 다루며 구현/화면 설계는 design.md 영역이다.
- 3인 이상 대결, 그룹 대결, 랭킹, 푸시 알림 — CLAUDE.md에 이미 범위 밖으로 명시.
- 품질전의 "승자 없음" 원칙 자체를 바꾸는 것.
- 대결 유형을 speed/quality 외에 추가하는 것.
- "각자 다른 과제로 성실성 경쟁" 모델, 대결 제목-개인 투두 연결 — 위 결정에 따라 채택하지 않는다.
- 속도전 승인에 제한시간을 두는 것 — 위 결정 8번에 따라 채택하지 않는다.

## 트레이드오프
- 속도전에 상대 승인을 요구하면 신뢰성은 높아지지만, 상대가 승인을 미루거나 이의제기를 남발하면 승부가 미확정 상태로 남거나 disputed로 빠질 위험이 늘어난다 — "속도전"이라는 이름이 주는 빠른 확정의 기대와는 다소 충돌할 수 있음을 감수한다.
- 완료(승부) 확정 시각을 "증거 제출 시각" 기준으로 정했기 때문에, 원래 속도전의 취지(먼저 끝낸 사람이 승리)는 유지되지만, 승인이 끝까지 안 나면 이긴 사람도 결과를 확정받지 못하는 채로 남을 수 있다.
- "이의제기 = 상대 완료 무효화" 규칙은 "대충한 사람이 먼저 눌렀다고 이기는" 상황을 막아주지만, 이의제기하면 자신이 승리할 수 있으므로 **악의적 이의제기 유인이 생긴다**(상대가 제대로 했는데도 이의제기해서 이기려는 시도). MVP에서는 지인 기반 2인 대결이라는 전제하에 이 위험을 감수하며, AI 심판(범위 밖, 배포 후)이 향후 이 문제의 해법이 될 수 있다.
- 양쪽 다 증거를 제출해야 종결되므로, 진 사람이 증거를 제출하지 않고 방치하면 대결이 끝나지 않고 계속 열려 있게 된다 — 이는 기존에도 있던 "방치된 대결" 문제와 같은 성격이며 이 문서에서 해결하지 않는다.
- 품질전 증거를 사진 필수로 격상하면 정체성은 확고해지지만, Storage 버킷/RLS/`image_picker` 도입이 이번 스코프로 당겨진다 — 이전 PM 피드백("배포 우선, 사진 증거는 이후로")과 배치되는 선택이며, 정체성 확립을 배포 속도보다 우선한 것으로 이해한다.
