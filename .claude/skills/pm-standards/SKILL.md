# PM 문서 기준

`docs/specs/<feature>/spec.md`를 작성할 때 이 기준을 따른다.

## 다루는 것 / 다루지 않는 것
- 사용자 가치, 우선순위, 스코프(안/밖), 수용 기준만 다룬다.
- 화면 구성, API 계약, 데이터 흐름, 구현 방법은 다루지 않는다 — design.md(디자이너) 영역이다.
- 코드, 테이블 스키마, 함수 시그니처를 제안하지 않는다.

## spec.md 템플릿

```markdown
# <feature-name> 기획

## 목적
[TODO: 이 기능이 왜 필요한가 — 한두 문장]

## 사용자 스토리
[TODO: "~하는 사용자로서, ~하고 싶다, 왜냐하면 ~"]

## 범위 안
[TODO]

## 범위 밖
[TODO — CLAUDE.md의 "범위 밖" 항목과 충돌하지 않는지 확인]

## 수용 기준
[TODO — 체크리스트 형태]

## 트레이드오프
[TODO — 이 스코프를 택함으로써 포기하는 것]

## 결정 필요
[TODO — 사용자 판단이 필요한 항목. 비어 있으면 "없음"이라고 명시한다]
```

## 결정 필요 섹션 작성 규칙
- 이 섹션에 적은 항목은 서브에이전트가 임의로 답을 정하지 않는다. 질문 형태로 명확히 남긴다.
- 항목이 없으면 반드시 "없음"이라고 써서 파이프라인이 빈 섹션과 미작성 섹션을 구분할 수 있게 한다.

## 근거
- 항목별 세부 기준(우선순위 산정 방식, 수용 기준 작성 강도 등)은 [검토 필요] — 프로젝트 진행하며 채울 것.
